# NAFv4.1 application-profile coverage

Generated by npm run build. Profile: `naf41-uaf` · `4.1.0-arch.16`.

**47 viewpoint IDs have structural application checks. This is not a claim of complete normative compliance.**

The runtime profile inherits the pinned UAF 1.0 catalog. The 81 additional node types and 122 additional relationships are explicit arch.js application mappings, not imported OMG stereotypes. See catalog.mjs and coverage.json for exact counts and rules.

NAFv4.1 p.80 states that its Information Model is conceptual and not intended for direct implementation. Accordingly, these adapters are a documented tool mapping. The separate native UAF constraints report remains applicable: ../uaf/COVERAGE.md.

NAFv4.1 p.91 labels the three C2 objectives Goal. The application type Goal extends the native UAF EnterpriseGoal and therefore inherits its attributes, relationship compatibility and C2 checks. EnterpriseGoal remains supported. This is an explicit source-vocabulary adapter, not a native UAF or ADMBw stereotype named Goal.

The C2 cut-out on p.90 explicitly permits desires from EnterprisePhase to Capability, EnterpriseVision and Goal. The adapters DesiresCapability, DesiresVision and DesiresGoal preserve these distinct endpoint types. Every planning phase requires at least one of these relationships; the p.91 example is accepted with DesiresVision and does not require an additional direct phase-to-capability link.

C3 permits specialization and grouping context without a CapabilityDependency at every displayed capability, following the SAR example on p.93. The application profile requires at least one dependency in the view; it cannot establish completeness against real-world dependencies.

C7 excludes EffectivenessCriterion and its subtypes from per-assessment-criterion mandatory characterization/evaluation checks, using connection nodesExclude selectors. These optional elements may therefore appear with only SpecifiesEffectiveness as on p.99. Ordinary assessment criteria still require characterization and incoming evaluation; measures and view-wide mandatory contents remain checked. EvaluatesCriterion follows Measure to AssessmentCriterion from the p.98 cut-out despite the reversed arrows on p.99.

C8 p.100 calls the concept Strategic Constraint; p.101 uses the displayed stereotype Constraint. Constraint is a concrete source-vocabulary subtype of StrategicConstraint, with an optional ruleKind restricted to Constraint (implied by its type, not inserted into attributes). Both use ConstrainsCapability toward Capability. OriginatesFromRationale follows the p.100 constraint-to-rationale direction; JustifiesStrategy remains the explicit inverse application link.

Cr reproduces p.103 using DeliversCapability, RelatesToEnterprisePhase, AggregatesEnterprisePhase and TriggersEnterprisePhase. Milestones may be implicit properties; visible milestones still require defining links, while capability/increment delivery checks remain mandatory. CapabilityIncrement now extends UAFElement directly, removing accidental ActualEnterprisePhase/Achiever/ActualState compatibility. The two phase adapters disallow cycles/self-links but do not enforce UML ownership, execution or phase-date ordering. See CR-MAPPING.md for source mapping and migration.

S1 supports the pp.104–105 Service vocabulary through an alias of native UAF 1.0 ServiceSpecification. The profile has 294 semantic node types plus 3 node aliases. ServiceGeneralization points from specialized to general service; SatisfiesServicePolicy follows service to policy as drawn in the source, while ServicePolicySatisfiedBy remains its explicit inverse. GroupsService relates group to service; AggregatesServiceGroup relates group to subgroup with an application-level cycle/self-link prohibition. The example explicitly supplies the inherited ServicePolicy.ruleKind; that value is not provided by the PDF. The documented UAF 1.2 rename is metadata, not complete cross-version equivalence; see ALIASES.md.

S2 pp.107–108 supports Node as an alias of the existing LogicalNode application subtype of OperationalArchitecture. PhysicalActiveResource is a concrete subtype of the abstract ResourcePerformer, retaining the required isStandardConfiguration boolean. ConsumesService (logical node to service), EnablesService (function to service), and RealizesService (physical active resource to service) preserve the source directions without changing native Consumes, IsCapableToPerform or Implements. ServiceAggregation represents the service aggregates links as solid directed grouping and is separate from the retained ServiceComposition relationship. Both reject cycles/self-links; no exclusive ownership or full UML ownership/lifecycle semantics are claimed. The p.108 example has nine nodes and eight relationships and validates strictly. The new S4 provider/consumer roles do not enable every optional p.107 S2 construct; S2-specific relies-on/delivers projections and role admission remain deferred. See README.md and the example naf41-service-structure.arch.

S3 pp.109–110 supports ServiceOperation as a vocabulary alias of native ServiceMethod (UML Operation), and DataProductType as a DataElement/PhysicalPassiveResource specialization. HasServiceOperationParameter and InvolvesPhysicalResource reproduce the visible has/involves links, including the parameter shared by two operations and the parameter without a resource trace. Owner/resource attributes remain typed, optional representations; S3 requires operation association through a link or visible owner reference, S7 requires both operation and resource association. Connection referenceAttributes count visible counterpart references without double-counting the same explicit edge endpoint. These are conceptual associations, not UML exclusive ownership; signatures, parameter ordering and simultaneous reference/edge consistency remain deferred. See README.md and naf41-service-interfaces.arch.

S4 pp.111–112 supports function-to-service EnablesService, recursive ServiceFunctionAggregation and all optional provider/consumer/activity patterns. Each selected function needs service coverage directly or via selected aggregation ancestors using the generic connections[].through rule. Legacy IsCapableToPerform remains accepted without changing its direction. Roles and binary links are application projections, not full UML ownership or executable behavior. See README.md and the two service-functions examples.

S5 pp.113–115 supports compact and objectified ServiceStateTransition forms. A typed transition reference binds the node to its state edge; referencedByAttributes enforces one selected binding per object and referenceConnectorLabels captions the is equal to connector. HasServiceState, triggers, state-to-function enables, function-to-mode has and nested state groupings cover the cut-out. Legacy owner/function/event references remain accepted; ownership checks move to selected S5 links/references. See README.md and the two service-states examples for limits.

S6 pp.116–118 supports ServiceInteraction in both namespaces, explicit RepresentsService, event triggers and relates-to-operation links. Typed interaction references bind object nodes to messages; the generic sequenceMessage flag separates messages from context. Sequence views draw object cards and attachments; showContext includes other selected nodes/links and orderAttribute validates/sorts unique positive positions. Compact represents/event/operation references remain valid. See README.md and the two service-sequence examples for renderer limits.

## Review still required

- Structural application mapping in arch.js; not the complete UML/SysML semantics or an official NATO/OMG implementation guide.
- No certification or complete NAF/UAF conformance is claimed. All 47 IDs are covered structurally, not all normative semantics.
- The inherited UAF coverage report still applies, including deferred native constraints. Application adapters are identified in type help.
- Only included view elements/links count toward viewpoint connection rules. Typed references resolve in the model; designated structural references must also be visible.
- NAF methodology, stakeholder approval, full state/sequence execution semantics and qualitative completeness require human review. See profiles/naf41/COVERAGE.md.

- **C2:** EnterprisePhase is the required planning-phase representation in this mapping; ActualEnterprisePhase can additionally record actual states. The C2 cut-out permits desires from an enterprise phase to a capability, vision or goal. Every planning phase requires at least one of these links; a direct DesiresCapability is not mandatory when DesiresVision/DesiresGoal is present.
- **C3:** Not every displayed capability must have a CapabilityDependency: specialization/grouping context is allowed, as SAR demonstrates in the p.93 example. The view requires at least one dependency; completeness of relevant real-world dependencies cannot be checked automatically.
- **C7:** EffectivenessCriterion and its subtypes are excluded from the per-assessment-criterion mandatory characterization/evaluation checks. Their links are optional, following p.98 and the Time to find example on p.99. Ordinary assessment criteria still require the complete capability-criterion-measure chain. EvaluatesCriterion is directed from Measure to AssessmentCriterion, following the p.98 cut-out. The evaluates arrows on p.99 are drawn in the opposite direction; that illustration does not change endpoint compatibility.
- **Cr:** The p.103 example omits explicit milestone nodes because milestones are properties of an increment. Cr therefore does not require visible CapabilityMilestone nodes or incoming DefinesIncrement at every increment. Explicit visible milestones still require a DefinesIncrement link; the optional milestones reference attribute may point to model elements outside the view. Implicit milestone completeness is not checked. AggregatesEnterprisePhase and TriggersEnterprisePhase are authored binary application adapters, directed whole-to-part and triggering-to-following phase. Each type is acyclic and disallows self-links as an application rule. No single-parent ownership, UML TemporalPart/slot semantics, execution, guards or date ordering between phases is inferred. CapabilityIncrement is a distinct UAFElement adapter, not an ActualEnterprisePhase/Achiever/ActualState. Earlier implicit compatibility with AchievedEffect and ActualEnterprisePhase relationships no longer applies. Optional startDate/endDate retain ISO date-time validation and ordering. Connected views reproduce the explanatory p.103 structure. A time-based Gantt representation needs actual schedule dates; the sample does not invent them.
- **S1:** Service aliases ServiceSpecification in both directions, preserving written labels and inherited service rules. This is not an implementation of the UAF 1.2 service metamodel. ServiceGeneralization points from the specialized service to its general service. Multiple inheritance is permitted by the profile; a whole-view tree still requires one hierarchy parent per node. SatisfiesServicePolicy points from service to policy, following pp.104–105. ServicePolicySatisfiedBy is the retained inverse application link, not a direction change to existing models. Native ServicePolicy still requires its ruleKind attribute; the p.105 drawing does not specify that value. GroupsService connects a ServiceGroup to a member service; AggregatesServiceGroup connects a group to a member group. The latter disallows self-links/cycles as an application rule, without imposing single-parent ownership or strong composition. Use a Connected view with a ServiceGeneralization-only tree group when policy/group context is present. A whole-view tree may filter to ServiceGeneralization, omitting non-hierarchy edges.
- **S2:** Node is an alias of the application LogicalNode, a subtype of OperationalArchitecture. This models the logical grouping/architecture meaning of a NAF Node, not a physical System, runtime instance or drawing template. The pp.107–108 directions are node to service (ConsumesService), function to service (EnablesService), and physical active resource to service (RealizesService). Native Consumes, IsCapableToPerform and Implements are unchanged; they are not interchangeable aliases of these adapters. ServiceAggregation projects whole service to member service (aggregates in the source), with a solid directed link and no exclusive ownership. ServiceComposition remains a separate relationship with composition notation. Both reject cycles/self-links; full UML ownership/lifecycle semantics are not implemented. ServiceDependency remains dependent service to required service. Per-service structural checks count ServiceAggregation/ServiceComposition/ServiceDependency, not optional node/function/resource traces. Service Consumer and Service Provider role projections and their relies-on/provides/delivers relationships are not yet implemented as dedicated NAF concepts; do not substitute generic nodes or native Consumes for those roles.
- **S3:** ServiceOperation is an application-profile vocabulary alias of UAF ServiceMethod (a UML Operation stereotype). DataProductType is a separate DataElement/PhysicalPassiveResource specialization. Native UAF and ADMBw definitions are unchanged. HasServiceOperationParameter runs from operation to parameter; InvolvesPhysicalResource runs from parameter to a physical passive resource/data product. The p.110 Geographic Location parameter is shared by two operations. These are conceptual associations, not exclusive UML Parameter ownership. Legacy owner/resource references remain valid and, when provided, must be visible. An owner reference can satisfy the required operation association instead of a has link; identical link/reference evidence is counted once. S3 does not require a resource for every parameter, matching the Resource parameter in p.110. An optional DataModel trace uses SpecifiesData from model to DataElement/DataProductType. A parameter does not link directly to a DataModel. Full UML operation signatures, parameter ordering/directions and consistency between simultaneous link/reference declarations require review.
- **S4:** Each selected function must enable a selected service directly or through selected aggregating ancestors. Legacy service-to-function IsCapableToPerform remains accepted. This is contextual coverage, not inheritance of behavior or implicit model edges. Provider and consumer are explicit contextual application roles, with optional represents references. Cut-out links are directed structural projections; no execution, notification delivery, exclusive ownership or full UML activity decomposition is asserted.
- **S5:** The transition node and edge share a type name in separate namespaces. Bind the object node via the edge transition attribute; is equal to is the graphical reference connector, not a separate edge with an edge ID as endpoint. Each selected transition object binds exactly one selected state edge. Legacy owner/function/event references remain accepted. State/mode ownership is checked in S5 through an explicit link or selected reference; duplicate contradictory ownership is rejected. Cross-state same-service consistency, conflicting event representations, guards, reachability, execution and omitted model elements require review.
- **S6:** Interaction objects bind exactly one selected lifeline message; message endpoints belong to the edge. Lifelines represent services and are not objectified interactions. Compact event/operation/represents references remain supported; explicit context links are optional. Sequence views support object cards and is equal to attachments. showContext true draws other selected cards and relationships in a context area. orderAttribute order sorts and checks unique positive message positions; otherwise declaration order or an explicit messages list determines display order. No execution, temporal constraints, UML fragments or event/operation-reference consistency is asserted.
- **S7:** Use ServiceOperationParameter or ServiceFunctionParameter: the unqualified UAF ServiceParameter lacks the required owner/payload projection. Operation parameters may use explicit has/involves links instead of owner/resource references; S7 requires both associations, whereas S3 makes the resource trace optional.
- **L2:** Needline source/target are references rendered in class details, not native UML AssociationClass ends. Structural hierarchy can use GroupsLogicalResource.
- **L2-L3:** Rich pictures/external illustrations and their interpretation require human review. This permissive concept view is intentionally not a substitute for formal viewpoints.
- **L3:** LogicalInteraction.conveyed is typed and nonempty; edge payloads may be shared with other views. UAF OperationalExchange may supplement, but not replace, the application interaction.
- **L5:** State-machine execution, same-owner transitions and guard completeness require review.
- **L6:** Interaction fragments, concurrency and sequence ordering consistency require review.
- **P1:** Resource/function taxonomy may consist of a single root; decomposition and classification completeness require review.
- **P3:** Protocol extends Standard, so a governing protocol also satisfies Standard membership. Matching the exact interaction protocol to both endpoint implementations requires review.
- **P5:** State-machine execution, same-owner transitions and guard completeness require review.
- **P6:** Interaction fragments, concurrency and sequence ordering consistency require review.
- **A1:** Glossary relevance and metadata completeness require review. Architecture descriptions and their native viewpoint references are optional here.
- **A2:** The native View.viewpoint reference and the drawn ConformsToViewpoint link must be kept consistent by the author.
- **A3:** The governing method is recorded as text; its domain-specific rule is not executed.
- **A4:** A non-tailored methodology can record an explicit no-extension decision and rationale. Process adherence requires review.
- **A6:** Succession is acyclic; version-label uniqueness, same-product succession and date ordering require review.

- **A8:** Applicability, compliance with standard contents and organizational ratification require review.

## Use of ADMBw reference

The supplied MDG technology declares NAF 4.0 plus Bundeswehr extensions. Its 318 domain stereotypes were inspected as data; diagram/toolbox stereotypes are not treated as domain classes. No MDG scripts, shape scripts, templates or images are executed or copied into the runtime.

StrategicConstraint supports the additional concept. ServiceDependency is restricted to service-to-service in this application profile. ContainsView, ConformsToViewpoint, StakeholderHasConcern and FramesConcern use the directions shown by ViewsInArchitecturalDescription, CompliesViewpoint, StakeholderConcern and ConcernForViewpoint. These are named application mappings, not an import of the entire ADMBw.

The inspected MDG defines EnterpriseGoal (a PropertySet / SysML requirement applied to Class), not a separate Goal stereotype. A dedicated ADMBw profile would be appropriate for Bundeswehr-specific vocabulary and constraints; the Goal adapter alone does not require one.

**Important differences:** ADMBw Evaluates relates FulfilmentCriterion to FitCriterion; it must not be reused as a synonym for NAFv4.1 Measure → AssessmentCriterion. ADMBw ImplementsProtocol starts at ProtocolImplementation; ResourceImplementsProtocol is an explicitly documented direct resource projection. Neither is silently substituted.
